# V2 Migration Documentation Mismatches

The official [Horizon TypeScript V2 Changes](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md) page is the clearest single statement of the V2 migration story, but several other current official pages still show older names, older import paths, or older event patterns. This document puts those sources side by side so graph search surfaces the contradiction instead of only one half of it.

## Import Path Changes Are Clearer Than The Examples

The [Horizon TypeScript V2 Changes](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#module-names) page says the `@early_access_api` prefix changed to `horizon`, with the core module becoming `horizon/core` and the NavMesh module becoming `horizon/navmesh`. The current [MeshEntity](../Reference/core/Classes/MeshEntity.md) reference, however, still contains example imports from `@early_access_api/v1`. That means the migration guidance and the generated example content do not fully agree, even though the modern V2 module names are the ones the rest of the documentation ecosystem points to.

For new code, the practical rule is simple: use `horizon/core` and `horizon/navmesh`, and treat `@early_access_api/*` imports in current official examples as historical carryover rather than supported V2 guidance. This interpretation matches the explicit migration page, and it also matches the rest of the current documentation tree that describes the V2 module family in `horizon/*` terms.

## Event Method Renames Are Still Mixed Across Official Pages

The [Horizon TypeScript V2 Changes](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis) page says the old [Component](../Reference/core/Abstract%20Classes/Component.md) event helpers [sendEntityEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), [connectEntityEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), [sendBroadcastEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), [connectBroadcastEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), and [sendNetworkEntityEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis) were renamed to the local and network method family on [Component](../Reference/core/Abstract%20Classes/Component.md). But the official [Events Best Practices](Events/Events%20Best%20Practices.md), [Broadcast Events](Events/Broadcast%20Events.md), and [Persistent Variables](Get%20started%20with%20TypeScript/Persistent%20Variables.md) pages still show [connectBroadcastEvent](Events/Events%20Best%20Practices.md), [sendBroadcastEvent](Events/Broadcast%20Events.md), and [connectEntityEvent](Get%20started%20with%20TypeScript/Persistent%20Variables.md) directly in example code.

That mismatch matters because the rename is not just cosmetic. The V2 naming split makes the local-versus-network distinction explicit in the [Component](../Reference/core/Abstract%20Classes/Component.md) API surface, which is easier to reason about than the older event helper names. If you are writing fresh V2 code, prefer the current [Component.connectLocalEvent()](../Reference/core/Abstract%20Classes/Component.md), [Component.connectLocalBroadcastEvent()](../Reference/core/Abstract%20Classes/Component.md), [Component.sendLocalEvent()](../Reference/core/Abstract%20Classes/Component.md), [Component.sendLocalBroadcastEvent()](../Reference/core/Abstract%20Classes/Component.md), and [Component.sendNetworkEvent()](../Reference/core/Abstract%20Classes/Component.md) family even when older official tutorials still show the legacy names.

## Visibility Method Names Conflict Between The Migration Page And The Guide

The [Horizon TypeScript V2 Changes](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#removed-apis) page says [Entity.setVisibleToAllPlayers()](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#removed-apis) was replaced by [Entity.setVisibilityForPlayers()](../Reference/core/Classes/Entity.md#setvisibilityforplayersplayers-mode), and that [Entity.setVisibleToPlayers()](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#removed-apis) was replaced by [Entity.resetVisibilityForPlayers()](../Reference/core/Classes/Entity.md#resetvisibilityforplayers). The current [Entity Visibility](API%20references%20and%20examples/Entity%20Visibility.md#updating-entity-visibility) guide still teaches [Entity.setVisibleToPlayers()](API%20references%20and%20examples/Entity%20Visibility.md#updating-entity-visibility) alongside [Entity.resetVisibilityForPlayers()](../Reference/core/Classes/Entity.md#resetvisibilityforplayers), while the current [Entity](../Reference/core/Classes/Entity.md) reference itself only publishes [Entity.setVisibilityForPlayers()](../Reference/core/Classes/Entity.md#setvisibilityforplayersplayers-mode) and [Entity.resetVisibilityForPlayers()](../Reference/core/Classes/Entity.md#resetvisibilityforplayers).

When migration prose and task-oriented guides disagree with the current [Entity](../Reference/core/Classes/Entity.md) reference, the safest choice is to follow the current reference surface. In practice that means using [Entity.setVisibilityForPlayers()](../Reference/core/Classes/Entity.md#setvisibilityforplayersplayers-mode) when you need per-player visibility control and [Entity.resetVisibilityForPlayers()](../Reference/core/Classes/Entity.md#resetvisibilityforplayers) when you need to clear overrides.

## Type Renames And Removals Are Not Applied Uniformly

The [Horizon TypeScript V2 Changes](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis) page says [IEntityStyle](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis) became [EntityStyle](../Reference/core/Interfaces/EntityStyle.md), but the current official reference still publishes [IEntityStyle](../Reference/unity_asset_bundles/Interfaces/IEntityStyle.md) as a real interface in the Unity Asset Bundles module. That means the rename is not a clean global replacement across the whole published reference surface.

The same kind of mismatch appears with [HorizonEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#removed-apis). The V2 changes page says it is no longer available and points creators toward [LocalEvent](../Reference/core/Classes/LocalEvent.md), but the official [CPU and TypeScript optimization and best practices](../Performance/Performance%20best%20practices/CPU%20and%20TypeScript%20optimization%20and%20best%20practices.md#local-events) page still recommends [HorizonEvent](../Performance/Performance%20best%20practices/CPU%20and%20TypeScript%20optimization%20and%20best%20practices.md#local-events) for purely local traffic, and the official [Marking Instances as Opened or Closed](API%20references%20and%20examples/Marking%20Instances%20as%20Opened%20or%20Closed.md) example still imports [HorizonEvent](API%20references%20and%20examples/Marking%20Instances%20as%20Opened%20or%20Closed.md). If your editor and the current reference do not surface [HorizonEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#removed-apis), treat those tutorial references as stale and prefer [LocalEvent](../Reference/core/Classes/LocalEvent.md) or [NetworkEvent](../Reference/core/Classes/NetworkEvent.md) based on delivery scope.

## Current Reference Pages Are The Most Stable Tie-Breaker

The current reference surface still uses deprecation language on some APIs instead of removing them outright. [ProjectileLauncherGizmo.launchProjectile()](../Reference/core/Classes/ProjectileLauncherGizmo.md#launchprojectilespeed) remains published but is marked obsolete in favor of [ProjectileLauncherGizmo.launch()](../Reference/core/Classes/ProjectileLauncherGizmo.md#launchoptions). [CodeBlockEvents.OnProjectileHitObject](../Reference/core/Variables/CodeBlockEvents.md) and [CodeBlockEvents.OnProjectileHitWorld](../Reference/core/Variables/CodeBlockEvents.md) remain published but point toward [CodeBlockEvents.OnProjectileHitEntity](../Reference/core/Variables/CodeBlockEvents.md). [INavMeshAgent.clearDestination()](../Reference/navmesh/Interfaces/INavMeshAgent.md#cleardestination) remains published but is marked deprecated in favor of setting [INavMeshAgent.destination](../Reference/navmesh/Interfaces/INavMeshAgent.md) to `null`.

That pattern is useful because it shows how the documentation set usually resolves migration drift over time: old APIs often remain visible long enough for existing code to stay understandable, but the current reference page carries the strongest signal about what new code should call instead. When official tutorials and official reference pages disagree, the most reliable default is to trust the current reference entry for the exact API you are about to use.

## A Conservative Migration Pattern For New Code

If you want the lowest-risk interpretation of the current documentation set, use this rule set:

- Prefer `horizon/*` module imports over `@early_access_api/*`, following [Horizon TypeScript V2 Changes](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#module-names).
- Prefer the local and network event helper names on [Component](../Reference/core/Abstract%20Classes/Component.md) over the older [sendEntityEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), [connectEntityEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), [sendBroadcastEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), [connectBroadcastEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis), and [sendNetworkEntityEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis) forms named in [Horizon TypeScript V2 Changes](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#renamed-apis).
- Prefer [Entity.setVisibilityForPlayers()](../Reference/core/Classes/Entity.md#setvisibilityforplayersplayers-mode) and [Entity.resetVisibilityForPlayers()](../Reference/core/Classes/Entity.md#resetvisibilityforplayers) over older visibility names mentioned in [Entity Visibility](API%20references%20and%20examples/Entity%20Visibility.md#updating-entity-visibility).
- Prefer [LocalEvent](../Reference/core/Classes/LocalEvent.md) or [NetworkEvent](../Reference/core/Classes/NetworkEvent.md) over [HorizonEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#removed-apis) when the current reference or your editor does not expose [HorizonEvent](API%20references%20and%20examples/Horizon%20TypeScript%20V2%20Changes.md#removed-apis).
- Prefer the current replacement named on any reference entry that carries deprecation text, such as [ProjectileLauncherGizmo.launch()](../Reference/core/Classes/ProjectileLauncherGizmo.md#launchoptions) or [INavMeshAgent.destination](../Reference/navmesh/Interfaces/INavMeshAgent.md).
